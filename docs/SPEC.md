# 자산관리 앱 — 제품 명세서

> Claude Code에 넘기기 위한 기획 문서. 코드는 Claude Code가 작성한다.

---

## 1. 한 줄 정의

**목표 금액과 기한을 넣으면, 매달 얼마를 저축·소비·투자해야 하는지 계산하고,
실제 지출을 추적해 이번 달이 빡빡한지 여유로운지 월중에 알려주는 앱.**

기존 가계부와의 차이: 가계부는 "얼마 썼다"를 기록한다. 이 앱은
**"목표 대비 지금 페이스가 맞는가"** 를 판정한다.

---

## 2. 설계 원칙 (이게 제일 중요)

### 원칙 1 — 숫자는 코드가, 말은 AI가
LLM에게 **절대 산수를 시키지 않는다.** 자산 앱에서 숫자가 틀리면 앱 전체 신뢰가 끝난다.

```
[결정론적 엔진]  →  구조화된 사실(JSON)  →  [LLM]  →  자연어 코칭
 필요저축액                                  "외식비가 평소보다
 필요수익률                                   249% 많습니다"
 여유/긴축 신호
```

LLM은 계산된 결과를 **설명하고, 우선순위를 정하고, 톤을 조절**하는 역할만.
비율은 엔진에서 미리 퍼센트로 변환해 넘길 것 (LLM이 곱셈하다 틀리는 것 방지).

### 원칙 2 — 목표가 비현실적이면 즉시 말해준다
대부분의 가계부 앱이 안 하는 것. **필요수익률 역산**이 이 앱의 핵심 차별점.

> 월 200만원 저축 / 3년 / 목표 1억 → **필요 연수익률 23.81%** → "비현실적, 목표 조정 필요"

이걸 계산해서 알려주지 않으면 그냥 예쁜 가계부다.

### 원칙 3 — 월말이 아니라 월중에 알려준다
월 끝나고 "많이 썼네요"는 쓸모없다. 경과일 비율로 외삽해
**"이 페이스면 예산 84만원 초과"** 를 20일차에 알려준다.

### 원칙 4 — AI 없이도 앱은 동작해야 한다
API 실패·오프라인·비용 절감 시를 위해 규칙 기반 폴백 요약을 반드시 함께 구현.
AI는 앱의 부가가치이지 생명줄이 아니다.

## 3. 기능 범위

### MVP
| # | 기능 | 설명 |
|---|---|---|
| 1 | 목표 설정 | 목표금액, 목표일, 현재자산, 기대수익률 |
| 2 | 소득 입력 | 월 실수령액, 연간 상여 |

  CSV 임포트로 대체하는 게 현실적**

## 4. 데이터 모델

```
User ─┬─ IncomeProfile   월실수령, 연상여, 기타부수입
      ├─ Goal[]          목표금액, 목표일, 현재자산, 기대수익률
      ├─ Account[]       예금/투자/부채 스냅샷
      └─ Transaction[]   날짜, 금액, 카테고리, isFixed
```

**`Transaction.isFixed`가 핵심 필드.** 고정지출(월세·보험·구독)과
변동지출(외식·쇼핑)을 분리해야 "줄일 수 있는 돈"이 계산된다.
이거 없으면 "덜 쓰세요"라는 조언이 무의미해진다.

카테고리 목록:
`housing, food, dining, transport, utilities, communication, insurance,
healthcare, education, shopping, leisure, subscription, debt, etc`

금액 단위는 전부 **원(정수)**. 부동소수점 금액 금지.

## 5. 계산 명세

### 5-1. 필요 월 저축액
기말납입 연금 미래가치:
```
FV  = PV·(1+r)^n + PMT·[((1+r)^n − 1) / r]
PMT = (FV − PV·(1+r)^n) · r / ((1+r)^n − 1)
r   = (1 + 연수익률)^(1/12) − 1
```
`r ≈ 0`일 때 0으로 나누므로 분기 처리 필수.

**검증된 기대값 (테스트에 그대로 쓸 것)**
| 조건 | 정답 |
|---|---|
| 1억 / 36개월 / 현재 0 / 연 3% | 2,659,711원 |
| 1억 / 36개월 / 현재 2천만 / 연 3% | 2,078,443원 |
| 1억 / 36개월 / 현재 0 / 연 0% | 2,777,778원 |

### 5-2. 필요수익률 역산 (이분법)
FV는 r에 대해 단조증가 → 이분법 안전. 탐색 구간 `[-0.5, 3.0]`, 200회 반복.
상한으로도 도달 불가면 `null` 반환 = "불가능".

**검증값**: 월 200만 / 36개월 / 목표 1억 / 현재 0 → **23.81%**

등급 판정:
| 필요수익률 | 등급 | 문구 |
|---|---|---|
| ≤ 4% | comfortable | 예적금으로 가능 |
| ≤ 8% | achievable | 적절한 분산투자 필요 |
| ≤ 15% | stretch | 공격적, 손실 가능성 안내 |
| > 15% 또는 null | unrealistic | **목표 조정 필요** |

### 5-3. 월중 지출 페이스
```
경과비율      = 경과일 / 그달 총일수
예상 변동지출 = 현재까지 변동지출 / 경과비율     ← 변동지출만 외삽
예상 고정지출 = max(이미 나간 고정지출, 과거 고정지출 중앙값)
예상 월말지출 = 예상 고정 + 예상 변동
```

| 조건 | 신호 |
|---|---|
| 예상 > 예산 × 1.05 | `tight` 긴축 |
| 그 사이 | `ok` |
| 예상 < 예산 × 0.90 | `surplus` 여유 |

`surplus`일 때 남는 돈 자동 배분 제안:
비상금 부족분 우선 → 나머지를 목표 60% / 투자 40%

### 5-4. 카테고리 이상 탐지
기준선은 **평균이 아니라 중앙값**. 이사·명절 같은 1회성 지출에 평균이 오염된다.
알림 조건: 편차 30% 이상 **AND** 절대금액 3만원 이상 (소액 알림 스팸 방지).
상위 5개만 노출.

### 5-5. 투자 여력
```
비상금 목표  = 월 고정지출 × 3~6개월 (기본 4)
투자가능액   = 유동자산 − 비상금 목표
```
비상금 미달이면 월 저축의 30%만 투자 배정 + 경고.

기간별 참고 배분 (**투자 권유 아님, 일반 원칙**):
| 남은 기간 | 성향 | 안전/채권/주식 |
|---|---|---|
| < 12개월 | 원금보존 | 100 / 0 / 0 |
| 12~36 | 보수 | 40 / 30 / 30 |
| 36~84 | 중립 | 15 / 30 / 55 |
| ≥ 84 | 성장 | 5 / 15 / 80 |

## 6. ⚠️ 함정 (프로토타입에서 실제로 발견된 버그)

Claude Code에 반드시 전달할 것. 안 적어두면 똑같이 밟는다.

### 함정 1 — 이미 다 쓴 카테고리를 외삽하면 전부 부풀려진다
20일차에 모든 카테고리가 일제히 "+55% 초과"로 뜨는 현상 발생.
월초에 결제가 몰린 카테고리(통신·보험)를 경과비율로 나누니 전부 뻥튀기된 것.

**해결**: 카테고리별로 지출 **분포**를 봐야 한다.
- 결제 건수 1건 + 과거에도 매달 1건 → 반복 결제로 보고 외삽 금지
- 여러 건 분산 → 외삽 적용

### 함정 2 — 하루 한도가 0원으로 표시됨
이미 예산을 초과했을 때 `max(0, ...)` 때문에 그냥 0원이 나온다.
사용자 입장에서 "하루 0원 쓰세요"는 무의미하다.

**해결**: 초과 상태면 한도 대신 **"이미 X만원 초과, 다음 달 예산에서 조정됩니다"** 로 문구 전환.

### 함정 3 — 필요수익률이 음수로 나오는데 등급은 "comfortable"
저축만으로 목표를 초과 달성하는 경우 필요수익률이 −9% 같은 음수가 된다.
계산은 맞지만 "−9% 수익률이 필요합니다"라고 표시하면 사용자가 혼란스럽다.

**해결**: 음수면 등급 문구를 **"저축만으로 목표 초과 달성 가능"** 으로 별도 처리.

### 함정 4 — 데이터가 없는 첫 달
과거 이력 0개월이면 중앙값·기준선이 전부 0이 되어 분석이 무의미하다.
**해결**: 이력 3개월 미만이면 분석 UI 대신 **"3개월 정도 기록하면 분석이 시작됩니다"** 온보딩 화면.

## 7. 기술 스택

```
Next.js 15 (App Router) + TypeScript
Prisma + SQLite      ← 로컬 우선
Tailwind + shadcn/ui
Recharts             ← 진척 그래프
Anthropic API        ← 서버 라우트에서만 호출
Vitest               ← 계산 엔진 단위 테스트 (필수)
```

**왜 로컬 SQLite인가**: 개인 금융 데이터는 유출 시 피해가 크다.
처음엔 로컬 DB로 만들고 필요하면 나중에 동기화를 붙이는 편이 안전하다.

### 폴더 구조 — 이 분리가 중요하다
```
src/
  core/                 ← 순수 함수만. React·DB·네트워크 의존성 0
    types.ts
    goal-engine.ts
    spending-analyzer.ts
    investment-advisor.ts
    __tests__/
  server/
    ai-coach.ts         ← Anthropic API 호출
  app/
  components/
```

`core/`를 프레임워크에서 완전히 분리할 것. 나중에 React Native로 모바일 앱을
만들 때 이 폴더를 통째로 재사용할 수 있다.

## 8. 개발 순서

1. `core/types.ts` + `core/goal-engine.ts` + **테스트** ← §5-1, §5-2 검증값 사용
2. `core/spending-analyzer.ts` + 테스트 (§6 함정 1, 2 반영)
3. `core/investment-advisor.ts` + 테스트
4. Prisma 스키마 + 마이그레이션 + 시드 데이터
5. 목표 설정 화면 → 대시보드 → 지출 입력
6. `server/ai-coach.ts` + 폴백 요약
7. CSV 임포트

**1~3번을 UI보다 먼저, 테스트와 함께 끝낼 것.**
계산이 틀린 예쁜 앱은 아무 쓸모가 없다.

## 9. 법적·윤리적 가드레일

- 특정 금융상품·종목·코인을 추천하지 않는다. **자산군 수준까지만.**
- 투자 관련 화면에는 원금 손실 가능성 문구를 상시 노출.
- "투자 권유가 아닌 일반적 참고 정보" 고지를 앱 내에 명시.
- 지출이 많았을 때 사용자를 비난하지 않는다. 다음 행동을 제시한다.
